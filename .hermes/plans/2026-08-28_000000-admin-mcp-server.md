# Admin MCP Server — Scope

**Status:** scope / not yet approved for implementation.

**Goal:** Expose Frona *instance administration* as an MCP server, so an MCP client
(Claude Code, or any other) can operate a self-hosted Frona deployment
conversationally — diagnose "is it up, who's locked out, why did that channel
stop", and then remediate.

**Recommended shape:** a new workspace crate `crates/frona-mcp-admin` producing a
single stdio binary that talks to the *existing* Frona REST API with a PAT. No
changes to the running server in Phase 1.

---

## Current Context

### What exists today

- **Admin REST surface** is small and policy-gated: `crates/frona-server/src/api/routes/admin.rs`
  covers users (list/create/patch/delete/deactivate/reactivate/set-password/unlock)
  and groups (list). Every handler runs through `require(..., PolicyAction::ListUsers | ManageUsers)`
  against the Cedar policy engine (`admin.rs:122`).
- **The rest of the operational surface is spread across route modules** —
  `system.rs` (health, info, version, log stream, restart), `config.rs`,
  `metrics.rs`, `usage.rs`, `policies.rs`, `tasks.rs`, `channels.rs`,
  `mcp.rs` (installed MCP servers + their logs), `skills.rs`, `agents.rs`,
  `vaults.rs`. All are merged flat in `main.rs:296-326`.
- **The MCP SDK is already vendored.** `rmcp = "1"` is a direct dependency of
  `frona-server` with `client` features; the `server` + `macros` features are
  already used in dev-dependencies. There is a working ~70-line rmcp *server*
  in `crates/frona-server/tests/bin/fake_mcp_server.rs` to copy the idiom from.
- **There is a precedent for "thin CLI over the Frona API":** `crates/frona-cli-mcp`
  (binary `mcpctl`) is a `reqwest` client reading `FRONA_API_URL` and
  `FRONA_TOKEN_FILE`, with its own compact human-readable output formatting.
  That crate is the closest existing analogue to what this proposes.
- **PATs exist:** `POST /api/auth/tokens` mints them; `ApiToken` carries
  `scopes: Vec<String>`, a principal, and an expiry
  (`crates/frona-server/src/auth/token/models.rs`).

### What's missing

- Frona *consumes* MCP servers; it does not *serve* one. There is no way for an
  external agent to administer an instance except by hand-rolling HTTP calls.
- No grouping of the operational endpoints into a coherent "admin" surface —
  they are discovered by reading route modules.

## Recommended Design

### Placement: a standalone stdio binary, not an in-server endpoint

`crates/frona-mcp-admin` → binary `frona-admin-mcp`, stdio transport,
`rmcp` with `server` + `macros`, `reqwest` client over the public REST API.

Why this over the alternatives:

| Option | Verdict |
| --- | --- |
| **(A) Standalone crate, stdio, REST client** | **Recommended.** Zero new attack surface on the deployed instance. Credentials stay on the operator's machine. Ships in the same repo and image, but releases independently of a server restart. Mirrors `frona-cli-mcp`, so the client, error mapping and output formatting have a template. |
| (B) MCP served from `frona-server` at `/api/mcp/admin` | Defer to Phase 3. Needs a new transport, new auth plumbing on a public route, and couples admin tooling to server deploys. Its one real advantage — no local binary — only matters for remote/hosted MCP clients. |
| (C) TypeScript/Node server | Rejected. The repo is Rust, `rmcp` is already a dependency, and a second language in-tree buys nothing here. |

The binary runs wherever the MCP client runs and reaches the instance over
HTTPS, so a remote instance (`https://<host>`) is served fine by stdio.

### Auth

`FRONA_API_URL` + a PAT from `FRONA_ADMIN_TOKEN` or `FRONA_ADMIN_TOKEN_FILE`
(mirroring `mcpctl`'s `FRONA_TOKEN_FILE`). Never a command-line flag — argv is
world-readable in `ps`. The PAT must belong to a user in the `Admins` group or
every Tier-0+ user tool returns 403.

### Tool surface, tiered by blast radius

**Tier 0 — read-only (~16 tools).** `health`, `system_info`, `version`,
`list_users`, `list_groups`, `list_agents`, `list_tasks`, `list_channels`,
`list_mcp_servers`, `mcp_server_logs`, `list_skills`, `list_policies`,
`get_config` (already redacted server-side), `get_metrics`, `user_usage`,
`chat_usage`.

**Tier 1 — reversible writes (~8).** `deactivate_user`, `reactivate_user`,
`unlock_user`, `start_channel`, `stop_channel`, `start_mcp_server`,
`stop_mcp_server`, `cancel_task`.

**Tier 2 — destructive or credential-touching (~7).** `create_user`,
`patch_user` (it can grant group membership), `set_user_password`, `delete_user`,
`update_config`, `restart`, `uninstall_skill`.

**Gating:** `FRONA_MCP_ADMIN_MODE=read-only | write | full`, defaulting to
`read-only`. Tiers above the mode are **not listed** in `tools/list` at all,
rather than listed-and-refused: the model cannot attempt what it cannot see, and
the advertised surface stays honest about what the session can do.

### Output shaping

Raw REST JSON is token-heavy and mostly noise for an operator question. Each
tool returns a compact rendering (users as `id · handle · groups · state`, one
per line) with a `raw: true` argument for the full object when something needs
drilling into. `crates/frona-cli-mcp/src/cli.rs` is the formatting precedent.

### Error mapping

401 → "PAT invalid or expired, mint a new one"; 403 → "this PAT's user is not in
the `Admins` group"; 429 → surface `Retry-After` (login lockout); 5xx → pass the
body through. An MCP error that names the fix is worth more than the status code.

## Findings that constrain this work

Three things surfaced while reading the current code. They are not blockers for
Phase 1, but two of them change what the tools are allowed to do, and the third
is a server-side bug waiting to happen.

1. **PAT scopes are issued but enforced nowhere.** `AuthUser::has_scope()`
   (`api/middleware/auth.rs:79`) has zero callers in the workspace; no route
   consults `scopes`. A PAT therefore carries the full authority of its user.
   *Consequence:* the tier gating above is a **client-side guard, not a security
   boundary** — anyone holding the token can bypass it with `curl`. It is worth
   having (it constrains the agent, which is the actual risk being managed) but
   the doc and the README must not claim more. Real enforcement is a separate
   server-side ticket.

2. **`/api/config` and `/api/system/restart` are not admin-gated.** Both take
   `_auth: AuthUser` and check nothing further (`config.rs:26,41`,
   `system.rs:132`) — any authenticated user can read the whole instance config
   and re-exec the process. Compare `logs_stream_handler` (`system.rs:78`),
   which explicitly gates on the admin capability, and all of `admin.rs`. This
   is a pre-existing privilege gap; file it separately rather than papering over
   it in the MCP layer.

3. **`update_config` deep-merges, and `get_config` redacts.** `update_config`
   (`config.rs:41`) merges the posted patch into the on-disk YAML, while
   `get_config` replaces secrets with a redaction placeholder. A naive
   read-modify-write through an MCP tool would therefore **write the literal
   redaction string over real secrets** (SMTP password, provider keys).
   *Requirement:* `update_config` accepts a **patch only** — never a whole
   config — and hard-refuses any string value equal to the redaction sentinel.
   This needs a test, not just a comment.

Also worth stating plainly: **`restart` kills the API the caller is talking to.**
The tool should say so in its description, and after firing, poll `/healthz`
until the instance answers rather than returning "restarting" and leaving the
model to guess.

## Phasing

**Phase 1 — read-only diagnosis loop.** The crate, the REST client, error
mapping, output formatting, and all Tier-0 tools. This alone covers "is it
healthy, who is locked out, which channel is down, what does the config say,
what do the MCP server logs show". No server changes. ~600 LOC.

**Phase 2 — remediation.** Tier 1 and Tier 2 tools, mode gating, the
`update_config` patch guard, and a two-step confirm for `delete_user`,
`update_config` and `restart` (first call returns the plan plus a confirm token,
second executes). ~400 LOC.

**Phase 3 — optional, separately ticketed.** Streamable-HTTP transport served
from `frona-server` for MCP clients that cannot run a local binary; server-side
PAT scope enforcement (finding 1); admin gating on config and restart (finding 2).

## Testing

- Unit: argument → request mapping, tier gating (assert `tools/list` shrinks in
  `read-only`), the redaction-sentinel refusal, output formatting.
- Integration: mock the Frona API (`httpmock`/`wiremock`) so tests need no live
  instance; drive the tool router in-process. `tests/mcp_e2e.rs` and
  `tests/bin/fake_mcp_server.rs` are the precedents for both halves.
- CI: a crate under `crates/*` joins the workspace automatically and must pass
  `cargo build --workspace --tests --keep-going --locked` (`.github/workflows/ci.yml:59`),
  so `Cargo.lock` has to be committed with it.

## Out of scope, deliberately

Per-user *data* — chats, messages, files, workspace contents. That is the
agent's surface, not administration, and it carries the largest privacy blast
radius. Likewise no vault item reads (`/api/vaults/{id}/items` returns credential
material) and no agent-impersonation tools.

## Open questions

- **One instance or several?** A profile mechanism (staging vs prod) is easy to
  add later and easy to get wrong now. Recommend a single env-configured
  instance for Phase 1.
- **Should Tier 2 require the two-step confirm, or rely on the client's own
  permission prompt?** Recommend the confirm token: it survives clients that
  auto-approve, and it makes the destructive plan reviewable as text.
